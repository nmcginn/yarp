# Configuration reference

Route configuration lives in `config/routes/`, one YAML file per application. This is the entire
config surface — there is no database, no admin UI, and no runtime write API.

If you are an application team adding or changing a route, read
[`contributing-routes.md`](contributing-routes.md) instead; this document is the schema and
validator reference.

## Why YAML, one file per application

- YAML because the file *is* the review artifact: comments matter and punctuation noise does not
  help a reviewer.
- One file per application minimizes merge conflicts when several teams change routes in the same
  week, and leaves the door open for per-app CODEOWNERS entries later.

## Loading

At startup the app reads every `*.yaml` file in `config/routes/`, merges them into a single model,
validates, translates to YARP types, and hands them to YARP's built-in `InMemoryConfigProvider`.
Non-YAML files (such as `README.md`) are ignored.

Files reach pods as a ConfigMap generated by CI from this repo, mounted at `/app/config/routes`.

**A config change triggers a rolling restart, not a hot reload** — see
[ADR 0002](decisions/0002-rolling-restart-over-hot-reload.md). Propagation takes a minute or two.

## Schema

```yaml
# config/routes/hr-portal.yaml
application: hr-portal
owner: hr-platform-team          # informational; surfaced in status UI and audit
routes:
  - routeId: hr-portal
    match:
      hosts: [hr.corp.example.com]
      path: "{**catch-all}"
    clusterId: hr-portal-svc
    authorizationPolicy: authenticated   # authenticated | anonymous
    requiredGroups: [hr-users, hr-admins]   # empty = any authenticated user
    identityHeaders: [userId, email, groups, displayName]
    caching:
      enabled: false
    auditLevel: standard                 # standard | detailed

clusters:
  - clusterId: hr-portal-svc
    destinations:
      primary:
        address: http://hr-portal.hr.svc.cluster.local:8080/
    healthCheck:
      active:
        enabled: true
        path: /health
        interval: 00:00:10
```

### Fields

**Top level**

| Field | Required | Notes |
|-------|----------|-------|
| `application` | yes | Logical application name. Should match the file name. |
| `owner` | yes | Owning team. Informational — shown in the status UI and audit events. |
| `routes` | yes | One or more routes. |
| `clusters` | yes | One or more clusters, referenced by the routes in this file. |

**Route**

| Field | Required | Notes |
|-------|----------|-------|
| `routeId` | yes | Unique across **all** files. Appears in audit events and metrics. |
| `match.hosts` | yes | Host patterns this route serves. |
| `match.path` | yes | YARP path pattern, e.g. `{**catch-all}`. |
| `clusterId` | yes | Must reference a cluster defined in some route file. |
| `authorizationPolicy` | yes | `authenticated` or `anonymous`. |
| `requiredGroups` | no | Empty or absent means any authenticated user. Ignored when anonymous. |
| `identityHeaders` | no | Which identity headers to send upstream: `userId`, `email`, `groups`, `displayName`. |
| `caching.enabled` | no | Defaults to `false`. Only permitted on anonymous routes. |
| `auditLevel` | no | `standard` (default) or `detailed`. |

**Cluster**

| Field | Required | Notes |
|-------|----------|-------|
| `clusterId` | yes | Unique across all files. |
| `destinations` | yes | Named destinations; `address` must pass the allowlist. |
| `healthCheck.active` | no | `enabled`, `path`, `interval` (`HH:MM:SS`). |

### This is a constrained domain model, on purpose

Raw YARP `RouteConfig` is **not** accepted in these files. The schema is a safety boundary: it is
parsed into internal types, validated, and then translated into YARP configuration. Widening the
schema to "just pass through YARP options" defeats the validator and, with it, the destination
allowlist.

## Validation rules

The same code runs in CI (`tools/ConfigValidator`) and at application startup. A failure at startup
is fatal and fails readiness.

1. Duplicate `routeId` or `clusterId` across all files.
2. Route referencing a nonexistent `clusterId`.
3. Two routes matching the same host and path precedence.
4. **Destination addresses outside the allowlist** of internal DNS suffixes and CIDRs — a security
   control, see [`security-controls.md`](security-controls.md).
5. Malformed host patterns, unparseable durations, unknown enum values.
6. `caching.enabled: true` on a route whose `authorizationPolicy` is not `anonymous`.

Validator errors must name the file and line number. Its output quality is what makes PR-based
self-service tolerable — it is the primary feedback surface for application teams.

```bash
dotnet run --project tools/ConfigValidator -- config/routes
```

## Environment overrides

`config/environments/dev.yaml` and `prod.yaml` carry environment-specific settings — the
destination allowlist, IdP endpoints, Redis and key ring locations, admin group for the status UI.
They are not route definitions; routes are identical across environments except where hosts differ.

## What happens when config is wrong

| Situation | Behavior |
|-----------|----------|
| Invalid YAML or a broken rule, caught in CI | PR check fails; nothing merges |
| Invalid config reaches a pod | Startup fails, readiness fails, rollout stalls, **old pods keep serving** |
| Route needs to be undone | `git revert` the PR and merge |

Git history is the version history, `git revert` is the rollback, and the PR is the audit record.
Configuration change auditing therefore does not appear in the runtime audit stream.
